# Kissa v2.5.1 — Universal Extreme Memory Architecture

_Status: implemented, tested, released._

## 1. The problem v2.5.0 could not solve

Important information was forgotten when the scene/context changed: a marriage could evaporate, a
character could forget a conversation that had just happened, and relationships read like strangers
again simply because the scene moved on. The root causes:

1. The only durable layers were **free-text memories** (facts/episodes) and a **numeric** world state.
   Neither could express *"MC and Poonam are married"* as persistent, verifiable state.
2. A single hallucinated reply could overwrite established state (the model's structured block was
   trusted as-is).
3. There was no way to ask *"what happened with Bhabhi before?"* — keyword overlap over a bag of rows
   cannot answer a question about a relationship pair.
4. There was no notion of **who knows what**: every character could act on global knowledge.

## 2. Architecture (one engine, every story)

```
                       ┌──────────────────────────── local device only ────────────────────────────┐
  AI / reader turn ──▶ │  detect events → validate transitions → accept/reject → persist → index   │
                       │                                                                            │
                       │  messages        raw archive, immutable (source of truth)                  │
                       │  story_events    typed · importance · pair keys · timeline · sources       │
                       │  relationship_states  current status + history per pair                    │
                       │  character_knowledge  who knows what · learned how/when · still valid      │
                       │  memory_contradictions  rejected state changes (traceability)              │
                       │  memory_index    inverted index (tokens + concept tags + weights)          │
                       └────────────────────────────────────────────────────────────────────────────┘
                                                   │
  current scene ──▶ query profile ──▶ index lane + structural lane ──▶ multi-hop ──▶ rank ──▶ bounded block
```

Modules:

| File | Responsibility |
|---|---|
| `src/lib/storyMemoryCore.ts` | Pure logic: concept lexicon, event detection, relationship ladder + `validateTransition`, knowledge extraction, query profile, ranking, multi-hop planner, timeline, consolidation, prompt rendering, structured-state parsing. No I/O. |
| `src/lib/storyMemoryStore.ts` | `StoryMemoryStore` interface + two implementations: SQLite (production, schema v7) and in-memory (tests/diagnostics). |
| `src/lib/storyMemory.ts` | Engine facade: `writeTurn`, `memorySearch` (the spec's memory-query API), `loadArchive`, `consolidate`, `migrate`, `buildContextBlock`, `stats`, `deleteForPlaythrough`; plus `recallStoryMemoryForPrompt` / `rememberTurn` helpers used by the chat screen. |
| `src/lib/engine.ts` | Prompt assembly (+ `LONG-TERM STORY ARCHIVE`, `CONTINUITY LAW`), and the hardened `kissa-state` stripping pipeline (`stripStateLeakage`, `finalizeAssistantText`). |
| `src/lib/db.ts` | Schema v7 DDL, archive dump/import for local backup, cascade deletes. |
| `src/screens/Chat.tsx` | Wiring: background migration, retrieval before generation, validated archive write after, consolidation cadence. |

## 3. Memory layers

- **Current context** — short-term window (unchanged, trimmed freely; trimming never touches the archive).
- **Persistent world state** — existing world-state engine (location, time, presence, numeric trust)
  **plus** the new persistent `relationship_states` (status + tier + history + sources).
- **Long-term event memory** — `story_events`: first meeting, confession, marriage, argument, promise,
  betrayal, important conversation, decision, discovery, object, location change, emotional beat,
  open task, knowledge exchange. Four importance levels (`VERY_HIGH/HIGH/MEDIUM/LOW`).
- **Character memory** — per-character facts, promises and interactions in events + knowledge records.
- **Relationship memory** — one record per pair (`player::poonam`, `player::bhabhi`, character pairs),
  with a full history of status changes.
- **Character knowledge** — `character_knowledge` records answer *who knows what, how, when, and
  whether it is still believed*.

## 4. Guarantees

| Requirement | How it is met |
|---|---|
| Nothing is forgotten on scene change | Scene changes write no state except explicit transitions; the archive is append-only. |
| Raw history is the highest authority | Every derived record stores `source_message_ids`; retrieval can pull the verbatim rows back (`evidence`). |
| AI cannot rewrite established state | `validateTransition` rejects downgrades without explicit break evidence and records a contradiction; a rollup never replaces its members. |
| Characters only know what they know | Knowledge is per character and injected as a map; retrieval is perspective-aware. |
| No cross-story contamination | Every table & query is scoped by `playthrough_id` **and** `story_id`. |
| Local-first / private | All tables live in the on-device SQLite file; the archive is never uploaded. Cloudflare still serves public story content only. |
| Fast with huge archives | Inverted index lane + bounded structural lane (recent 150, open items, milestones, per-character knowledge) — candidates stay bounded no matter how long the saga is. |
| No paid/external service | Concept lexicon + aliases + stems + trigrams + local inverted index. |

## 6. Manual QA performed

- Story A (arranged-marriage wala love, MC + Poonam): marriage → 10 scenes later a scene treats them
  as strangers → state stays `married`, contradiction logged.
- Story B (MC + Bhabhi): important secret conversation → Poonam scene → Bhabhi returns →
  "Bhabhi ke saath pehle kya hua tha?" retrieves the MC↔Bhabhi event (paraphrased wording).
- Restart: a fresh engine over the same store returns relationships, events and knowledge.
- Long run: 300 exchanges (600+ raw rows) with the important event at message 1 — still retrieved,
  prompt size bounded.
- Isolation: Story A memory never appears in Story B queries (and vice versa).
- Legacy journey: migrated from raw messages, relationship seeded from the legacy numeric score,
  second run is a no-op.

## 7. Privacy & Cloudflare

- User memory stays local: `story_events`, `relationship_states`, `character_knowledge`,
  `memory_index`, `memory_contradictions` are SQLite-only; backups are user-initiated local files.
- The story backend (`https://beyondredeye.site/api`) is untouched: it still serves published story
  content, covers and manifests, and receives no user data. `worker` tests + content validation pass.
